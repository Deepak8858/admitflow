# AdmitFlow scoped IAM bootstrap runbook
These tools generate **review-only policy and request JSON candidates**; they never attach policies, obtain credentials, execute AWS requests or provision resources. No cloud resources are assumed to exist. `input.example.json` contains only the approved identity/name contract, not discovered certificate, secret, key or load-balancer identifiers. `fixtures.mjs` contains clearly synthetic identifiers **only for offline tests**; never use it as deployment configuration.
## Safety and ownership
The lead alone reviews and executes cloud changes after approval. The default workflow uses verified non-root MFA sessions, not the root/default profile. The operator's temporary first-release exception is documented in [release gates](../../docs/release-gates.md#temporary-human-operator-exception); it defers only the human non-root/MFA prerequisite, not scoped CFN/workload permissions, provider evidence or acceptance. Generated policies/trust and DNS root rejection remain unchanged. No credentials in this directory and no paid build authorization implied.
Both user-to-role trust policies require the exact deploy user and `aws:MultiFactorAuthPresent=true`. Verify this condition against the actual temporary-credential/login flow; browser MFA is not evidence that the STS request has that key. Do not replace the condition with `IfExists` to get a login working.
Generated role permissions are a reviewed **complete set**, not safe to union with preexisting broad policies. The lead must inspect attached policies, groups, boundaries, trust, SCPs and relevant resource policies. Workload boundaries are ceilings, not permission grants: CDK still supplies role policies. Create the six boundary policies once as bootstrap-owned policies under `/admitflow/boundaries/prod/`, with exactly the names in the manifest. Routine identities cannot create/version/delete policies or replace/remove workload boundaries.
## Offline commands
Run `npm run test:iam` (or `node infra/iam/verify.mjs`) for syntax and tests in the repository's isolated environment; no dependencies, AWS SDKs or credentials are needed. The raw test command is `node --test infra/iam/policies.test.mjs`. The central verifier, `node scripts/verify.mjs --all`, also runs this IAM runner. The infrastructure test glob `infra/tests/*.test.ts` alone does not discover this directory.
Use `node infra/iam/generate.mjs --help` and `node infra/iam/validation.mjs --help` for syntax. Generation is `node infra/iam/generate.mjs <phase> <identifier-input.json> <new-output-directory>`. Prefer an ignored `.data/iam-review/<phase>` output directory; an existing output directory is rejected. The input must contain every exact fixed field from `input.example.json`, plus the verified identifiers needed by that phase. Unknown fields are rejected: never pass runtime environment files, JSON secret values, tokens or credentials. There is no environment/profile fallback.
Example safe first-phase generation: `node infra/iam/generate.mjs prerequisites infra/iam/input.example.json .data/iam-review/prerequisites`. This writes JSON only. Later phases fail if their required identifiers are absent; copy the contract to a local identifier-only input and add actual returned identifiers after separately authorized lead operations. Syntax validation cannot prove provenance: the lead must verify ownership, region and physical resource identity.
## Phases and required inputs
1. **prerequisites** — needs only the fixed contract. Produces exact-user bootstrap trust and separate managed-policy families for certificate request, application-secret creation, service-linked-role creation, DNS inventory and the one-off log-resource-policy write. Request ACM for precisely `admitflow.incfrog.ai`, public DNS validation, RSA_2048, and `Application=AdmitFlow`, `Environment=prod` request tags. The application secret creation is exactly `admitflow/prod/application`, using the default AWS-managed Secrets Manager key, with these tags and no replication. An existing customer-key secret is handled in the next phase; creation with a customer key needs separate review, not a guessed ARN. The six-character `??????` suffix in a creation policy is an IAM match for the service-generated suffix, not an invented complete ARN.
2. **secret-update** — requires the actual complete `applicationSecretArn`, and explicit `applicationSecretKeyMode` (`aws-managed` or `customer-managed`). The latter also requires actual `applicationSecretKmsKeyArn`. Allows value population/update and metadata only on that existing secret; the customer-key branch scopes `Decrypt`/`GenerateDataKey` to that exact key, Secrets Manager ViaService and exact SecretARN encryption context. Transfer runtime values separately through the protected secret workflow, not generator input.
3. **certificate-metadata**, then **dns-validation** — certificate-metadata needs only the actual `certificateArn` returned by RequestCertificate and grants DescribeCertificate on that exact ARN. Use it to discover the validation record before generating dns-validation. The latter requires actual `certificateArn` and actual ACM-returned normalized `validationRecordName` (lowercase, no trailing dot). It permits CREATE only for that one CNAME in the fixed zone. Inspect conflict/delegation state with the DNS tooling. The record target is not an IAM condition: DNS preview/apply must validate the real ACM target.
4. **tenant-key-create**, then **tenant-key-configure** — creation needs only the fixed contract; configuration requires the actual returned `tenantKeyArn`. These are separate temporary bootstrap permission sets, not additions to routine deployment permissions. Creation omits tags; configuration tags and manages only the exact key and creates only its fixed alias. Follow the mandatory sequence below, including key-policy cleanup before IAM detachment.
5. **deployment** — requires actual `applicationSecretArn`, explicit key mode (and key ARN if customer-managed), actual `certificateArn`, and the verified bootstrap-owned `tenantKeyArn`. Produces operator/deploy trust, stack-only CloudFormation permissions, the bounded CFN service-role families, six distinct workload boundaries, workload trust, and separate GitHub publishing trust/permissions. Web/worker boundaries name only the exact tenant key; there is no tagged-key wildcard fallback. Optional `queueSecretArn` tightens the queue name+suffix scope after that resource exists. Do not invent these IDs. Boundary setup/tightening is a separate lead-owned IAM change; CFN cannot perform it.
6. **release-operator** — requires the actual `migrationTaskDefinitionArn` **including its exact revision**. Produces only a separate review candidate, **no trust and no automatically selected attachment role**. It permits RunTask for that revision in `admitflow-prod`, Exec disabled; PassRole for only migration task/execution roles to ECS tasks; DescribeTasks in that cluster; and migration-log reads. The lead must choose/approve a scoped non-root identity and review the immutable image revision and networking. API RunTask overrides/network choices are not fully restricted by these IAM conditions; execution-role access to the shared JSON secret makes this application-admin authority. Service desired-count transitions remain stack parameter updates through the deploy role; there is deliberately no direct UpdateService shortcut.
7. **dns-application** — requires actual `certificateArn`, `loadBalancerArn` for `admitflow-prod-alb`, and `targetGroupArn` for `admitflow-prod-web`. It permits only application-name A CREATE (no AAAA baseline, UPSERT, DELETE, apex, mail, wildcard or WWW). It also permits exact service/certificate metadata and regional ELB load-balancer/listener/target-group/target-health metadata reads. Actual ALB IDs are required for review, but ELB Describe operations cannot be ARN-scoped by IAM. DNS tooling must verify ALB alias target/zone, HTTPS listener certificate, service/release readiness and conflicts. Do not attach this write phase before service acceptance.
Detach obsolete bootstrap-phase permissions instead of accumulating their authority. In particular detach the one-off log-policy write after reviewing readback. Generated operator assume-bootstrap and assume-deploy policies are separate; union only as explicitly approved. The publisher role name/attachment and the GitHub OIDC provider's existence must be verified by the lead; trust is fixed to `repo:Deepak8858/admitflow:ref:refs/heads/main` and `aud=sts.amazonaws.com`. No PR, alternate branch, environment-subject fallback, secrets read, RunTask, deployment or PassRole is included in publisher permissions.
## Tenant key bootstrap and cleanup
This is the default non-root operator sequence, **not an executable workflow**. Generated `requests/*.json` are API-input candidates, and `resource-policies/*.json` are independently inspectable policy documents. Authorize each cloud step separately; normally use the exact non-root bootstrap role with verified MFA/account/region. For the temporary root-operated exception, separately review the initial/final policy path described in [release gates](../../docs/release-gates.md#temporary-human-operator-exception); do not blindly apply a temporary bootstrap-role grant or skip lockout safety, inventory, disabled creation retries or final readback.
1. Inspect existing key/alias inventory and release records under separately reviewed read permissions before granting creation authority. An existing alias/key is a reuse/conflict review, not permission to replace it. Generate `tenant-key-create` from the fixed contract and review `requests/create-key.json` against `resource-policies/tenant-key-initial.json`. It has no `Tags`, uses `SYMMETRIC_DEFAULT`, `ENCRYPT_DECRYPT`, `AWS_KMS`, single-region, and explicitly sets `BypassPolicyLockoutSafetyCheck=false`. IAM allows only Singapore CreateKey with no tag-key context and denies lockout bypass. There is no IAM wildcard PutKeyPolicy or TagResource allow.
2. The initial policy enables account IAM delegation and temporarily grants **only the exact bootstrap role** direct PutKeyPolicy on this new key for the creation safety check. In a key policy, `Resource: "*"` means that attached key, not all account keys. Account delegation requires corresponding IAM permission; it does not itself give routine roles KMS administration. Review all principals and effective policies before granting this phase.
3. After explicit creation approval, disable automatic SDK/CLI retries (`AWS_MAX_ATTEMPTS=1` for AWS CLI), pin the standard Singapore endpoint/region and verified named profile, submit once, and preserve the actual returned KeyId/Arn and request evidence. **CreateKey has no idempotency token.** On timeout, interrupted output or ambiguous response, stop and reconcile CloudTrail/inventory under separately approved read access; never resubmit merely because no ARN was captured. This phase deliberately does not grant account key inventory.
4. Put only the actual returned ARN into an identifier-only input, generate `tenant-key-configure`, and replace creation authority with its exact-key setup policy. Do not union the phases. Read DescribeKey and GetKeyPolicy; confirm account/region/ARN, enabled state, symmetric encryption usage/spec, AWS origin, single-region and the expected initial policy. ARN syntax alone proves none of these properties. Stop on any mismatch.
5. Apply the reviewed tag and rotation requests to that exact key. Paginate ListAliases and reject the fixed alias if it targets any different key; do not update/delete aliases. If the exact alias already targets this key after an uncertain submission, verify that outcome instead of blindly recreating it. Otherwise create the reviewed alias. Verify both exact tags, rotation enabled, metadata/state and the alias target with readback. ListAliases is an explicitly regional-wide metadata exception only in this temporary phase.
6. **Before detaching setup IAM permission**, apply `requests/put-key-policy.json` with lockout bypass false. Its final policy contains only account IAM delegation and removes the entire temporary direct bootstrap grant. Keep exact-key IAM PutKeyPolicy attached for the safety check. Read GetKeyPolicy back and structurally compare with `resource-policies/tenant-key-final.json`; do not infer success from a submitted request. On uncertainty retain the scoped recovery permission, stop deployment and inspect readback. Never use lockout bypass to force progress.
7. Only after verified final-policy/readback evidence, detach setup policies and verify no other effective bootstrap grant remains. **IAM detachment alone does not remove direct resource-policy permission.** Recheck effective denial of bootstrap key administration and routine deploy/CFN/publisher administration. Record nonsecret identity, key ARN, alias, tags, rotation and cleanup evidence; use the same verified key ARN for production context and workload boundaries.
The key and alias are durable **bootstrap-owned resources outside the application stack**. `Key.fromKeyArn` is a CDK reference, not a CloudFormation resource import: production emits no Key/Alias resources and no deletion/retention policy for them. Stack rollback/deletion cannot clean them up; they can continue to incur charges. Do not automatically delete, replace or repoint the key/alias during failure recovery. Preserve the key and historical ciphertext access with database backups; later key administration requires a separately reviewed exact-key grant.
Residual authority: CreateKey cannot constrain arbitrary initial policy JSON or the number of new keys. During setup, PutKeyPolicy can grant other principals access to this exact key. The reviewed artifacts, short-lived access and mandatory readback are operational controls, not IAM document-content enforcement. Neither tenant-key phase grants key deletion, disabling, alias update/delete, crypto use or CreateGrant. Live IAM/key-policy validation remains required before execution.
## Per-service policy scope
- **CloudFormation:** change-set operations authorize the **stack ARN** `stack/AdmitFlow-prod/*`, not a fabricated change-set ARN. Mutating create/update/change-set/delete/rollback calls must explicitly supply the exact `cloudformation:RoleArn`; PassRole is exact and only to `cloudformation.amazonaws.com`. ExecuteChangeSet inherits the stack's service-role authority. `ResourceTypes` cannot be combined with `CAPABILITY_NAMED_IAM`; there is deliberately no claim of a runtime resource-type allowlist. Anyone granted stack mutation effectively controls the application within CFN's permissions. No default CDK bootstrap administrator role is authorized.
- **IAM:** six exact workload role ARNs; CreateRole and PutRolePolicy/UpdateAssumeRolePolicy require the matching `iam:PermissionsBoundary`. PassRole is only these roles to `ecs-tasks.amazonaws.com`. No managed-policy attachment, boundary removal/replacement or bootstrap identity mutation. IAM cannot inspect arbitrary trust-policy/inline-policy JSON: a deployer can alter workload trust within these identities and ceilings. Review trust changes; boundaries do not validate principals.
- **EC2:** only the VPC/subnet/route-table/internet-gateway/security-group resource types, account and region. Creation requires both application request tags; CreateSubnet/CreateRouteTable/CreateSecurityGroup separately require a tagged parent VPC. Existing mutation requires application resource tags. CreateTags is only permitted as the dependent action during the enumerated create operations (`ec2:CreateAction`), so unrelated resources cannot be relabeled into scope. Post-create tag changes/removals are intentionally not allowed. Route destinations, SG rules and network attributes remain application-network administrator choices, not a precise packet-level IAM fence.
- **ECS/ECR/ELB:** repository, cluster, services, task-definition families, ALB and target-group names are fixed. ELB CreateListener authorizes the parent ALB; CreateRule authorizes its listener. Generated suffixes stay under the fixed names. RegisterTaskDefinition supports family ARNs; **DeregisterTaskDefinition cannot be ARN-scoped**, and DescribeTaskDefinition is also regional-wide. This permits deregistration of unrelated task-definition revisions in this region by CFN and needs explicit residual-risk approval. The publisher may upload/pull only the application repository; the auth-token action has no resource scope.
- **ElastiCache:** named replication group/subnet group and their member/snapshot candidate prefixes only. Native `AWS::ElastiCache::ParameterGroup` has no configurable physical-name property: `admitflow-prod-cacheparameters-*` is a **fail-closed candidate, not a proven naming guarantee**. Parameter-group create requires request tags; subsequent mutation/use requires existing tags, and it cannot be retagged from unrelated scope. CFN snapshot physical naming similarly needs verification against the scoped `admitflow-prod-queue-*` prefix. Do not widen on a deployment error. Validate handler naming/tag propagation before deployment; unresolved evidence is a blocker.
- **KMS:** only the two temporary bootstrap phases administer the tenant key; routine deploy, CFN and publisher policies contain no KMS actions. Creation permits no tags; subsequent tagging, rotation and policy update are exact-ARN-only. Alias creation separately authorizes only `alias/admitflow-prod-tenant-credentials` and that same key. Workload boundaries permit crypto operations only on the verified key; unrelated keys remain outside scope even if tagged identically. See the sequence and residual key-policy/quantity risks above.
- **Secrets:** CFN owns only the named queue secret, with generated suffix scope until tightened; it has no application-secret read/update grant. Execution boundaries permit the actual application secret ARN, plus queue secret for web/worker only. The migration **task** boundary denies all AWS actions. Its execution role still reads the same complete application secret: ECS JSON selectors are **not field-level IAM isolation**, so any principal controlling images/task definitions can extract application secrets, including migration credentials. This is not tenant/admin isolation; separate physical secrets would be a different design.
- **Logs/alarms:** named log groups/streams/alarms, separate execution-log ceilings per service. `logs:PutResourcePolicy` and `logs:DeleteResourcePolicy` are absent from routine CFN; DeleteResourcePolicy is not granted even to bootstrap. The one-off PutResourcePolicy cannot restrict policy name or document contents in IAM and therefore can affect account log policies in Singapore. Review and apply only `resource-policies/valkey-log-delivery.json` as `admitflow-prod-valkey-logs`, preserving unrelated policies. CFN retains regional-wide `Create/Get/Update/Delete/ListLogDeliveries` and metadata read exceptions. Log-delivery mutation is an explicit regional residual privilege, not exact-resource IAM.
- **DNS/ACM:** exact public zone and normalized record name/type/action conditions, with `Null` checks as well as `ForAllValues` to prevent missing-context allowance. ACM request permissions cannot be ARN-scoped before a certificate exists; names and DNS method are constrained. IAM cannot enforce record values/alias target, certificate issuance state, ALB readiness or existing-record conflict checks. This phase must be combined with the reviewed DNS tooling, not treated as self-sufficient validation. GetChange can read any change status because IDs are not known before submission.
### Additional handler and ARN evidence
The existing image-publishing workflow reads final digest evidence using `ecr:DescribeImages`, so publishing permits that metadata read on **only** `repository/admitflow-prod` in Singapore; it does not permit repository-wide inventory elsewhere. Before requesting a new certificate, the prerequisite role has a separately labeled `acm:ListCertificates` regional metadata exception for paginated reuse inventory. ListCertificates cannot be certificate/domain scoped by IAM; the lead must filter and verify the actual certificate ARN, then generate the exact-ARN certificate-metadata phase for DescribeCertificate. Prerequisites do not grant wildcard DescribeCertificate.
The [CreateKey API](https://docs.aws.amazon.com/kms/latest/APIReference/API_CreateKey.html) requires dependent TagResource permission only when creation includes tags. The separate untagged creation request avoids that dependency without granting wildcard existing-key tagging. The [PutKeyPolicy API](https://docs.aws.amazon.com/kms/latest/APIReference/API_PutKeyPolicy.html) safety check remains enabled throughout. [ListAliases](https://docs.aws.amazon.com/kms/latest/APIReference/API_ListAliases.html) cannot be alias-name-scoped, so only temporary configuration gets its regional metadata exception. Production no longer emits `AWS::KMS::Alias`; CFN has neither KMS handlers to execute nor alias inventory permission. This offline design still needs actual identity/key-policy validation before a live bootstrap.
CloudWatch's [LogGroup API](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_LogGroup.html) explicitly says to use the ARN ending in `:*` in IAM policies for most API actions; the exceptions are `TagResource`, `UntagResource`, and `ListTagsForResource`, which require the plain ARN. The existing CreateLogGroup/retention/metric-filter policy therefore retains `log-group:<exact-name>:*`; Resource-tagging APIs remain on plain exact-name ARNs. [CreateLogGroup](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_CreateLogGroup.html) separately requires TagResource or TagLogGroup for create-time tags, both already scoped here. Offline ARN-shape regression checks preserve this documented distinction; actual AWS authorization remains untested.
## Validation and release gates
`node infra/iam/validation.mjs <verified-identifier-input.json> <new-output-directory>` exports `SimulateCustomPolicy` input files plus expected-case metadata; it performs **no AWS call**. A combined input needs deployment, both DNS and release-operator identifiers. Some deliberately hypothetical resource IDs (other stack/VPC/key/role) are test vectors, not claims those resources exist. Boundary cases evaluate the ceiling alone, not a complete role session.
The offline matcher tests only the emitted Action/Resource/Condition subset. It does not prove AWS semantics, supported principals, every multi-resource dependency, service-control policies, key/resource policy interaction, trust/session behavior, deletion rollback, CFN tagging or actual resource existence. The selected public SAR metadata fixture checks action existence, condition names and resource-scope availability; it aggregates supported conditions and is not a substitute for checking the exact action/resource row. Re-review AWS documentation when refreshing it.
Before any attachment/provisioning the lead must:
1. Review generated JSON, protected identity inventory and all residual authorities above; confirm no existing unrelated resource is already tagged into the application scope.
2. Validate policy documents with IAM Access Analyzer; execute real AWS IAM simulations for the exported positive and negative inputs, collect MissingContextValues and investigate differences. Also test actual identity policies **intersected** with boundaries, trust and applicable SCP/resource/key policies. Do not call the offline matcher an AWS simulator.
3. Validate KMS untagged creation and both policy safety checks, exact-key setup, alias multi-resource authorization and final cleanup/readback. Separately resolve parameter-group and snapshot naming, ACM/ElastiCache tag-at-create dependencies, account service-linked-role existence, CloudFormation role cleanup behavior and operation coverage using current resource-provider schemas/handler documentation. Boundary deletion is intentionally denied; any handler requiring it during rollback/deletion needs lead review, not automatic bypass. Existing EC2 tag updates likewise intentionally fail closed.
4. Check compact synthesized template size and bootstrapless role configuration in the infrastructure workstream. No template-bucket/assets/S3 bootstrap or IAM-admin workaround is included.
5. Validate actual MFA temporary-credential role assumption for the default non-root workflow. Only that human prerequisite is deferred under the dated operator exception; verify exact caller/account/region for every path and preserve all trust conditions. Retain provider/build/migration/backup/DNS acceptance gates from the deployment runbook and release-gates addendum. The DNS helper continues to reject root/default profiles.
Every managed-policy family is split at statement boundaries under 6,144 non-whitespace characters and checked against the default ten managed-policy attachments per identity. Trust policies stay under the default 2,048 characters. Do not concatenate these into a user inline policy (2,048-character quota) or one role inline policy (10,240 aggregate quota). Boundaries are separate managed policies attached as boundaries, not regular identity-policy grants. Existing SignInLocalDevelopmentAccess and any future operator attachments still count toward user quotas.
